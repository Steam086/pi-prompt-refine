# RPC `/refine` verification

The extension supports `/refine optimize <draft>` in Pi RPC mode, with **manual viewing** via the `/refine result <runId>` command in the receipt. Use the full ID from the receipt, including its binding suffix, in the original session. Reloading or changing the session or branch invalidates that ID. The optimizer must already be configured. Viewing a result does not rerun the optimizer, adopt edits made in the viewer, or send anything to the main Agent.

## Why the result does not open automatically

Pi RPC provides a prefilled multiline `editor` but no way for the extension to check the host composer or detect a host-owned dialog. In [T3's reference source revision](https://github.com/pingdotgg/t3code/tree/344de5fe8e70e9eeaacaedc34e7aa5e2a29287d1), the [Pi adapter routes the request to its thread](https://github.com/pingdotgg/t3code/blob/344de5fe8e70e9eeaacaedc34e7aa5e2a29287d1/packages/provider-pi/src/server/adapter.ts#L1864-L1928) and [passes the prefill through](https://github.com/pingdotgg/t3code/blob/344de5fe8e70e9eeaacaedc34e7aa5e2a29287d1/packages/provider-pi/src/server/adapter.ts#L4400-L4412). The [renderer uses the composer for the pending answer](https://github.com/pingdotgg/t3code/blob/344de5fe8e70e9eeaacaedc34e7aa5e2a29287d1/apps/web/src/components/chat/ChatComposer.tsx#L3859-L3865). Opening it at completion could take over the input surface while the user is typing. The extension opens it only on an explicit `result` command and does not open it while a Pi dialog or result editor is active or while the main Agent is streaming. It waits for the editor to close before returning from `result`; T3 can cancel pending prompts when their turn settles.

Two host limitations remain:

- T3 [ignores `notify` outside an active turn](https://github.com/pingdotgg/t3code/blob/344de5fe8e70e9eeaacaedc34e7aa5e2a29287d1/packages/provider-pi/src/server/adapter.ts#L1804-L1825). A late failure or timeout notice may not be visible there; querying the scoped result ID still reports its status.
- T3's [composer send snapshot trims text](https://github.com/pingdotgg/t3code/blob/344de5fe8e70e9eeaacaedc34e7aa5e2a29287d1/apps/web/src/components/ChatView.logic.ts#L1393-L1404), so the extension cannot preserve trailing draft whitespace removed before the RPC call. It preserves the draft it receives after the single body delimiter and passes the full candidate back without trimming.

## Evidence and outstanding checks

- **Pi RPC 1.6.0, Linux x86_64, isolated profile:** Before implementation, a synthetic slash probe returned `handled` before emitting a delayed editor request. The prefill survived RPC byte for byte. After implementation, a separate process loaded the real extension and a synthetic optimizer. Invalid slash input returned usage, one optimization produced one request with the exact draft, and explicit viewing and reopening delivered all 262,144 UTF-16 code units unchanged. Confirming edited text and cancelling did not change the candidate or add Pi transcript messages.
- **Root regression tests:** The mocked editor received the full 2,097,152-code-unit result, including leading and trailing whitespace, Chinese, blank lines, a URL and nested code fences. Tests also exercise queueing, duplicates, out-of-order and immediate completion, failures, timeout, cancellation, invalidation, and stale result IDs. This tests the extension boundary, not a browser clipboard or renderer.
- **Unmodified T3 desktop/browser:** Source review only (desktop package version `0.1.11` at `344de5fe`). The live slash route, origin-thread behavior across a thread switch, draft and dialog protection, scrolling to the last line and selection/copy equality in a narrow window have **not** been verified. Repeat with synthetic short and near-limit texts in an isolated unmodified host before marking either manual viewing or full T3 support as accepted. No T3 patch, deployment, restart, or real provider call was used for these checks.
