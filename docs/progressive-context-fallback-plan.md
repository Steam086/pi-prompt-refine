# 渐进式上下文补充草案

**状态：实验设计讨论，尚未实现。** 当前有界项目背景注入与历史选择已经实现，模型主动补充协议尚未实现。本文记录实验目标、候选方案与未决问题，不代表实现授权或确定的配置协议；后续实验计划在独立 worktree 中进行。方向总览见 [设计原则与演进方向](../DESIGN.md)，当前行为见 [上下文说明](context.md)。

## 需求与边界

当草稿的关键指代或约束无法从首轮输入确定时，按需补充相关背景，而不是默认发送全部历史或编造缺失事实。这与候选修订独立：补足一次改写的信息，不是调整已有结果，也不是网络失败重试或授权 optimizer 执行任务。

实验目标：

- 渐进式披露为可选功能，默认关闭；关闭时维持现有单次请求行为。
- 每次优化最多两次逻辑模型调用，争取大部分场景一次完成；单次完成率是待验证目标，不是已知效果。
- 优先改善首轮完整语义段落的选择，关键缺口才补充；初版不依赖全量段落评分。
- 不抢焦点，不自动改稿或发送，不把优化中间过程写入主会话。

## 设置语义与首轮策略

“是否允许补充请求”和“首轮发送多少背景”是不同决策，不应由含义不明的 `best_effort` 同时控制。候选模式如下，名称及配置结构尚未确定：

| 模式 | 首轮背景 | 补充请求 | 定位 |
| --- | --- | --- | --- |
| `bounded` | 现有有界历史 | 不允许 | 默认行为与实验基线 |
| `progressive` | 有界完整段落与有界来源索引 | 最多一次 | 用户显式开启的实验模式 |
| `full_if_fits` | 预算内全部可见历史 | 不允许 | 完整历史优先的对照策略，不必作为首版产品选项 |

若采用“总开关 + best_effort 策略”，总开关仍默认 Off；`best_effort` 仅表示开启后尽量一次完成、必要时补充，不能隐式开启功能或默认上传全部历史。

“不截断”建议解释为尽量保留完整消息或语义段落，超预算时省略完整项并标注，不是无限量上传承诺。当前默认历史限制为 12 条、16,000 字符，另有模型窗口预检；完整历史优先策略若绕过前一层限制，必须是显式选择，且仍受模型容量和输入预算约束。

初版建议仅从当前分支的可见 user/assistant 文本补充，不自动开放 thinking、工具结果、摘要或文件正文。历史被用户关闭时，不得通过补充请求重新开放；来源索引本身也属于向 Provider 披露的数据，须有范围与长度限制。

## 两阶段协议与触发条件

候选流程：

1. 首次请求既能直接返回最终 `prompt`，也能返回结构化 `need_context` 与所需来源 ID；不要把首次请求变成必经的规划调用。
2. 宿主校验 ID、来源授权、是否有新增内容及剩余预算，从冻结来源池取出片段。模型仍无工具，不能指定任意文件读取或执行任务。
3. 第二次请求只允许返回最终结果，不再允许补充；仍有歧义时保留不确定性，不编造、不发第三次请求。

补充建议同时满足：缺口会影响指代、约束或授权范围；获准来源池中存在可能解决缺口的未披露内容；剩余时间及输入、输出预算允许。历史状态为 `partial` 或“更多背景可能更好”本身不足以触发补充。

无效 ID、重复请求、无新增内容、来源耗尽或预算不足时不继续调用；具体失败呈现与回退协议仍待确定。第二次失败不能把 `need_context` 当作候选或伪装成成功；已有候选保持不变。

“最多两次”指扩展最多发起两次逻辑模型调用，SDK 传输重试或 WebSocket/SSE fallback 的物理网络请求次数需另行区分。

## 成本、延迟与触发频率

缓存读取成本约为普通输入的 10% 可作为实验假设，不是所有模型或 Provider 的统一费率，也不是第二次总成本或耗时只有 10%。新增输入、两次输出、可能的缓存写入费用另计；命中的输入仍占模型上下文窗口。

设首次输入为 B，第二次新增输入为 A，补充触发率为 p。若旧输入全部命中、缓存读取单价比例为 0.1，忽略输出等费用，则普通输入 token 等价成本为：

```text
平均输入成本 ≈ B + p × (0.1B + A)
```

例如 B = 6k、A = 14k：触发率 20% 时约为 8.92k，100% 时约为 20.6k。相比一次上传 20k，频繁补充可能得不偿失。此例仅说明冷启动下的简化关系；完整历史对照组也可能命中缓存，实际比较必须采用相同缓存条件。

若旧输入仅有比例 h 命中，第二次旧输入成本应改为 `B × [(1 − h) + 0.1h]`，不能预设全部命中。实际费用按所用模型的读取、写入及输出价格核算。

平均耗时可粗略看作“首轮耗时 + p × 补充阶段耗时”。首轮判断是否缺信息也可能增加耗时；缓存不能消除第二次往返、排队或输出生成。因此少发输入不必然更快，低触发率也不必然更好：还需检查模型是否遗漏了本应补充的关键背景。

上下文评分反映当前 prompt 的侧重点，后续目标变化时未必能复用；低相关性也不代表授权或禁止事项可以安全删除。评分自身的推理和输出成本由当前请求承担，后续收益不能预设，故不作为初版补充协议的前提。

## Cache key 与可复用前缀

缓存字段注入方案见 [cache key 讨论](cache-key.md)。以下为实验应保留或补足的约定，不代表已实现或已测得缓存收益。

### 缓存分组与 SDK 会话分离

- 继续使用 `modelRegistry.streamSimple()`，通过 `onPayload` 补充 `prompt_cache_key`；不为此设置 SDK `options.sessionId`，避免引入连接复用、continuation 等额外客户端状态。
- 初版仅面向已核验的官方 provider/API/endpoint；保留已有 hook 和已有 key，显式 `cacheRetention: "none"` 时不补 key，不强制覆盖缓存保留策略。
- 两阶段采用相同 key，作用域为“扩展命名空间/key 方案版本 + 请求捕获的 Pi session + 实际 provider/API/model/endpoint”。不加入阶段编号、requestId、roundId、时间戳、草稿或完整输入哈希。
- 可复现用的 payload 哈希与缓存分组 key 分开。key 不是权限隔离机制，来源授权仍由宿主校验。

### 追加式输入候选方案

当前 `buildRefineInput()` 的历史状态和计数位于历史正文前；第二次重建 JSON 并改变这些字段，会提前打断共同前缀。相同 key 不保证相同前缀，更不保证实际缓存命中。

可考虑以下布局：

```text
第一次：相同 system + user（首轮冻结输入）
第二次：相同 system + 原封不动的首轮 user
        + assistant（结构化 need_context 文本）
        + user（补充片段与最终阶段标记）
```

两阶段 system 保持一致，阶段变化放在追加内容中；不回写首轮历史计数，不要求重放 thinking。协议需明确如何按 ID 补全摘录及处理重复内容。这只是同一次优化内的短暂上下文，不写主会话、不无限累积修订链。

第二次仍须容量检查，优先预留补充空间；若因预算改变首轮前缀，就不能继续假设旧输入全部命中。该布局会改变现有单条 JSON user 消息结构，应与“仅补 cache key”分开验证。Provider 的缓存边界和保留规则也可能影响复用，需实测。

### 观测而非承诺

区分 key 是否正确发送、前缀是否可复用、服务端实际命中量及最终费用。沿用现有 `cacheRead`、`cacheWrite` 等字段，但需保存逐阶段用量与累计值；不能只展示第二次，也不能重复累加已包含在其他字段内的 token。缺失统计不能伪造为零。

先串行验证重复输入，再验证相同背景不同草稿、两阶段追加、冷/热缓存及并行情况。没有显式 key 也可能命中，不能把一次命中直接归因于新 key。

## 冻结、预算与生命周期

- 当前 `HistorySnapshot` 保存筛选后的历史；渐进式方案需在 round 捕获时另保留有界、获准的补充来源，区分“本地可用”和“已发送”。补充不能临时读取已经变化的 live branch。
- 两阶段属于同一次运行，共用请求身份、取消信号、总超时、失效边界和并发槽位；第二次不重新获得完整超时额度。
- 保留逐阶段实际输入、预算诊断、输出和用量。当前单份 `preparedInput`/`sentInput` 不足以描述两次调用，不能直接覆盖首轮记录。
- 发送边界、归档、跨 round 迟到结果及 session/分支切换沿用现有规则，不让迟到响应影响新任务。
- 两阶段除各自窗口预检外，还需累计输入、输出、时间及可得费用的预算边界。

## 实验评估与未决事项

比较现有有界单次请求、渐进式补充、完整历史优先三种策略，使用相同草稿和冻结来源，并区分冷/热缓存条件。记录：

- 单次完成率、补充触发率，以及应补未补、不必补却补的情况。
- 补充是否真正解决缺口，硬约束保留、无依据新增、指代和授权范围是否正确。
- 平均与 P95 延迟、逻辑调用次数、逐阶段及累计 token、实际缓存命中和可得费用。

收益以硬约束保留和改写质量不下降为前提，不能仅以 token 减少、评分合理或低触发率判断成功；真实模型评估不能由协议 mock 测试替代。

仍需确定：

| 事项 | 未决问题 |

| 来源与索引 | 首轮段落如何选择？来源索引粒度、长度和冻结池容量如何限定？ |
| 协议 | `need_context` 的字段、ID 校验、摘录补全、无新增内容及无效输出如何处理？ |

| 缓存 | 各 Provider 的实际支持、缓存边界、命中率和收费如何验证？ |

本轮仅整理讨论；配置字段、模块划分、协议细节及实现方案须在后续实验中明确。
