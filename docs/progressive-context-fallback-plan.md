# 渐进式上下文补充草案

**状态：待讨论，暂不实施。** 当前有界项目背景注入与历史选择已经实现，模型主动补充协议尚未实现。本文件只保留未决设计问题，方向总览见 [ROADMAP](../ROADMAP.md)。

## 需求与边界

当草稿的关键指代或约束无法从首轮输入确定时，按需补充相关背景，而不是默认发送全部历史或编造缺失事实。

这与“根据反馈修订上一候选”独立，也不是网络失败重试或授权 optimizer 执行任务。当前仍是单次无工具调用，返回 `prompt` 和可选 `title`；输入结构见 [上下文说明](context.md)。

## 尚需确定

| 事项 | 需要回答的问题 |
| --- | --- |
| 披露来源 | 是否允许更多 user/assistant 原文、已有摘要、工具元信息或结果片段？哪些始终排除？ |
| 首轮输入 | 如何固定原稿、可访问历史边界与初始背景？如何先改好首轮选择，避免无谓补读？ |
| 定位与粒度 | 先提供来源索引还是直接提供片段？如何保留来源、区分摘要与原文、标记不可用内容？ |
| 授权与协议 | 谁判断信息不足？补充是否逐次确认？是否使用受限结构化请求，如何拒绝越界？ |
| 预算与终止 | 如何限制调用次数、累计输入、时间和费用？重复、无新增信息、历史耗尽或仍不足时如何结束？ |

## 评估要求

- 信息足够时不补充；不足时只提供获准且相关的新内容，缺失仍无法解决时保留不确定性。
- 补充步骤共享同一次逻辑请求的身份、累计预算、取消、超时和失效规则，不让迟到响应影响新任务。
- 保持不抢焦点、不自动改稿或发送、不写入优化中间过程的现有边界。

范围、授权、协议和停止规则需讨论确认后再实施；本草案不预设新增配置字段或模块。
