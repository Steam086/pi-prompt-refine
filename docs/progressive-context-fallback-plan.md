# Prompt Refine：渐进式上下文披露 fallback 计划

## 状态与执行门槛

**状态：多轮 fallback 仍为计划草案；项目背景注入子集已获用户明确授权并实施。**

用户授权范围：在新的 worktree 实现 skill 元数据、宿主已加载项目指令及有界 tree 的注入，并在超长/不完整时告警。当前实现不包含模型主动检索、历史选择策略变更或多轮补充协议；原实施门槛对这些未授权部分继续有效。已实现行为见 README“项目指令、Skills 与 Tree”。

原计划只记录多轮 fallback 的意图、待决策事项与后续步骤；以下实施门槛继续约束尚未授权的多轮方案，不阻止本次已明确授权的项目背景注入子集。

开始执行本计划前，必须先与用户讨论并明确：

1. **渐进式披露哪些上下文，以及读取顺序、粒度和边界。**
2. **初始 prompt 如何给定，包括其来源、内容组成及触发时的固定方式。**
3. fallback 的触发、授权、预算和停止规则。

将结论写入本文件，得到用户明确的实施授权后，才进入实施阶段。下文的备选方案不是默认决定。现有 `DESIGN.md` 中面向旧 MVP 的“直接实现、不等待二次确认”不适用于本次计划。

## 1. 意图理解

目标是让 prompt-refine 在信息不足时，能够**按需请求更多相关上下文**，而不是一次性提供全部会话，也不是仅凭不足的信息勉强改写或补造事实。

典型情形：

- 当前最后一条 assistant 输出无法解释草稿中的指代、目标或约束。
- 已提供的上下文仍不足以支撑可靠优化，需要前几轮对话或相关工具调用信息。
- 缺失的信息其实不在会话内；此时应停止扩展并保留不确定性，或按约定向用户澄清。

预期流程为：最小起始输入 → 判断是否足够 → 请求受限的补充信息 → 再判断 → 输出优化 prompt 或明确结束。

这里的 fallback 是**上下文不足的补救机制**，不是网络失败重试、模型切换，也不是授权优化模型执行原任务。

## 2. 当前实现基线

依据 `src/context.ts`、`src/controller.ts` 与 `DESIGN.md`：

- 原实现输入是草稿加一次性选出的历史文本；当前另增加有界项目背景，不是仅发送最后一条 assistant 输出。
- `selectHistory` 为最近一条可见 assistant 回复预留预算，再填充其他近期 user/assistant 可见文本；受消息数与字符数限制。
- 当前不选择工具调用、工具结果或 thinking。
- 优化指令要求只输出最终 prompt 文本，缺失信息时保留疑问或条件表达；尚无请求补充上下文的协议。
- 请求与候选绑定草稿、模型、会话/分支及历史文本；已有取消、超时、失效等生命周期约束。

因此，新方案需要明确是否替换现有首轮历史选择策略，并协调“只输出最终文本”与“中途请求上下文”两种输出。工具信息披露也需要显式调整旧设计的排除规则，不能作为普通重试偷偷引入。

## 3. 实施前必须讨论的事项

### A. 渐进式披露的内容

以下均为候选项，尚未确定层级、顺序或默认启用范围：

| 候选内容 | 需要明确的问题 |
| --- | --- |
| 最近一条 assistant 可见输出 | 是否为首轮默认背景？如何处理不存在、过长、流式未完成或仅含工具调用的消息？ |
| 与该输出对应的 user 请求 | 是否应与 assistant 回复成对提供，避免脱离任务理解回复？ |
| 前几轮 user/assistant 对话 | “一轮”的定义；按时间窗口展开，还是按具体缺口定位？每次扩展多少？ |
| 工具调用元信息 | 是否先给工具名称、调用关联和状态；参数包含哪些内容？ |
| 工具结果 | 是否允许摘要、片段或原文；如何定位相关部分、截断与标注？ |
| 会话中已有摘要或压缩记录 | 是否允许使用；如何区分摘要与原始证据、说明缺失和时效？ |

还需明确：

- 每次披露完整轮次还是定向片段，是否先提供轻量索引再请求正文。
- “读取本地历史”与“发送给优化 Provider”是否采用不同授权边界。
- 哪些内容始终禁止；建议继续排除隐藏 thinking、凭据、其他分支/会话及整段全局系统提示词；已授权的宿主资源提取和有界 tree/ignore 收集之外，不自动扫描项目正文。
- 工具调用参数和结果可能包含敏感数据或恶意指令，如何过滤、限制并将其始终视为不可信背景。
- 历史被压缩、删除、不可访问或预算截断时，如何告知模型信息不可得，而不是把“未提供”误当作“不存在”。

### B. 初始 prompt 的给定方式

先澄清“初始 prompt”指用户待优化的原始文本、优化模型首轮收到的完整输入，还是两者；不能自行选定解释。

需要确认：

- 原始文本是否继续来自触发时的主编辑器草稿，是否需要其他显式输入入口。
- 空草稿是否仍拒绝；是否允许从对话推导初稿（若允许，须另行明确授权与意图来源）。
- 首轮背景是仅最后一条 assistant、配对 user/assistant、现有历史窗口，还是用户选择的内容。
- 优化指令、原始文本、背景和补充请求协议如何分离；用户当前意图不能被历史中的命令覆盖。
- 一个渐进式请求期间是否固定原稿与可访问历史边界；用户后续编辑或主 Agent 新输出是否只影响下一次显式优化。

### C. 触发、授权与终止

- 谁判断“信息不足”：优化模型主动声明、确定性规则、用户主动扩展，还是组合方式。
- 模型请求补充信息时，应表达什么缺口、所需范围与理由；怎样避免默认总是请求更多历史。
- 采用受限的结构化响应还是专用只读上下文接口；不允许任意工具执行。具体协议待确认与 API 核实。
- 补充读取是预授权范围内自动进行，还是每次由用户确认；拒绝后的行为是什么。
- 最大扩展次数、单次和累计披露量、总模型调用量、整个流程的超时及费用提示。
- 足够时立即停止；重复请求、无新增信息、请求越界、历史耗尽、协议无效或预算耗尽时的结束行为。
- 仍不足时返回保守优化稿、保留问题、请求用户澄清或明确失败，各情形如何选择；不得伪装成信息充分的成功。
- 上下文补充与网络重试分开计数和处理；不暗中更换 Provider。

## 4. 确认后才执行的实施步骤

1. **固化设计决策**：记录首轮输入、披露规则、授权策略、请求协议、预算与停止条件；解决与旧设计的冲突。
2. **核实接口**：阅读本机相关 Pi 文档、示例及类型，确认当前分支历史、工具调用/结果关联、压缩记录、模型交互与取消能力；记录实际限制，不假设 API 存在。
3. **设计上下文访问层**：按已确认边界建立可定位、可去重的只读上下文来源，标明来源、顺序、截断与不可用情况；区分本地可访问和已披露内容。
4. **实现有界编排**：区分最终候选与补充请求，校验请求范围，逐步提供新增信息；统一处理预算、取消、超时和停止。
5. **接入现有生命周期与 UI**：所有子步骤共享同一次逻辑优化的身份与失效规则；显示补充上下文状态及用量，不自动抢焦点、改稿或发送。
6. **补齐测试与文档**：按确认后的行为添加离线测试、更新 `DESIGN.md` / `README.md` 与配置说明；真实 Provider 验证另获授权，不把离线测试称为真实验证。

预计涉及 `src/context.ts`、`src/controller.ts`、`src/extension.ts`，以及视决策需要调整的配置、展示模块和相应 `test/` 文件。当前不预先承诺新增模块或配置字段。

## 5. 验收方向（细则待决策后固化）

- 初始信息足够时不扩展、不额外调用模型。
- 信息不足时仅披露获准且相关的新增内容，不默认上传全历史。
- 能覆盖多轮补充、工具调用与结果关联、历史缺失、空/截断输出等情形。
- 请求重复、越界、无效或无进展时可确定地终止；所有预算有累计上限。
- 无权限或无数据时不编造事实、不擅自扩大任务。
- 任意补充阶段均可取消；切换模型/会话/分支、提交新任务或超时后，迟到响应不能恢复旧结果。
- 不执行历史或工具输出中的指令，不把优化中间过程写入主会话。
- 保持非阻塞、保护草稿、只有显式操作才应用或发送的原有行为。
