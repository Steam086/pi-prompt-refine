# 设计原则与演进方向

Pi Prompt Refine 帮用户在当前对话中表达意图并检查候选。任务执行和最终提交由用户所在的主 Agent 流程负责。近期决策见[路线图](roadmap.md)，文档入口见[索引](index.md)。

## 已采用的取舍

- **分离生成和采用。** 改写可以排队、失败或产生多个候选。保留用户草稿及操作目标，让用户独立决定编辑、接受或发送。
- **比较共享背景，优化模型独立。** 同一 round 冻结背景，使并行比较有共同起点。模型选择可以偏向响应快、成本低且足以理解本次对话的模型。改写质量需要结合真实理解与用户意图评估。[冻结背景](context.md#round-快照) · [语义验收](optimizer-evaluation.md)
- **偏好来自显式选择。** 关键词难区分引用中的要求和本次意图。分开表达改写偏好与主 Agent 要求，让用户知道将采用哪份指令。独立快照避免库更新改变过去选择。[偏好指南](preference-selection.md)
- **历史以审阅为主。** 旁车保存足以阅读和比较的历史，并限制持久化敏感输入。恢复后使用新的 round 重新优化，完整旧请求复现需要单独设计。[历史与清理](tui-guide.md#local-history-and-cleanup)

## 上下文选择与预算

先验证单次请求内的背景选择和 token 估算，用相同草稿和冻结来源对照保真、延迟与花费。技术现状见[预算预检](context.md#发送前统一预算)。

- **相关性选择。** 在用户允许的来源内优先保留近期纠正、授权边界及指代依据。若按草稿选择，比较和重试仍应保留共同选择依据。
- **渐进补充。** 仅在关键证据不足时考虑显式启用有界补读。关闭的来源继续关闭，补充从冻结的获准来源中读取，沿用取消、时限和成本约束。将额外调用和可能重复计费的前缀纳入对照，与单次有界输入及完整历史优先比较。展开协议和成本推导见 Git 中 `1d5b26d:docs/progressive-context-fallback-plan.md`。
- **Provider 缓存。** 如研究按会话提供 cache key，先明确可披露的标识、Provider 范围和前缀稳定性。相同 key 无法保证命中。用冷／热对照和实际 cache usage 证明收益，避免无意引入 SDK 连接或续传状态。旧版 SDK 的方案及限制见 Git 中 `1d5b26d:docs/cache-key.md`。

## 偏好与历史分析

先用现有 Preferences 和 Revise 测量高频复用的操作成本、授权保真和连续修订漂移。若再考虑推荐，仍由用户明确选用。历史导出或复现先确定最小字段与保留期限，完整输入快照需明确的数据保存授权。
