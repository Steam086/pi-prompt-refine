# 设计取舍

| 决策 | 原因 |
| --- | --- |
| 生成、接受、发送分别触发 | 同一原稿可以产生多个候选。用户可以继续比较、修订，或接受其中一份回到编辑器再决定是否发送。[使用说明](usage.md) |
| 比较共享背景，优化模型独立 | 冻结本轮的来源，让不同模型从同一份原稿和背景出发。各次请求仍按所选模型的容量做预算。[上下文协议](context.md) |
| 显式选择偏好并保存快照 | 原稿可能引用别人的指令，关键词不足以判断用户要采用哪一条。保存所选版本也让用户能追溯一次改写用了什么要求。[偏好指南](preference-selection.md) |
| 历史用于审阅 | 候选需保留完整正文才能再次采用。省略超限的整条记录，减少敏感数据落盘。恢复后的任务可在当前轮次复制原稿并用新背景运行。[历史保存与隐私](configuration.md#历史保存与隐私) |

## 评估新的上下文策略

用相同草稿和冻结来源比较单次请求的保真度、延迟和用量。检查近期纠正、指代和授权边界在裁剪后是否仍有依据。连续修订还要检查有效编辑是否被撤销、已删除的要求是否再次出现。[预算预检](context.md#发送前统一预算) · [语义验收](optimizer-evaluation.md)

若评估额外的背景读取，只从用户已启用且冻结的来源取材，将额外请求和重复前缀计入延迟与费用。若评估 Provider 缓存，先确认可披露的标识，再用实际的缓存读写用量比较冷、热请求。
